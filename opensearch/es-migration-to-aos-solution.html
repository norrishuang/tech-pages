推荐原则：日志类、时间滚动、保留期明确且允许等待的域，优先采用“升级到 2.19 → 等待旧索引全部自然删除 → 升级到 3.7”的路径；混合业务域只对长期保留索引执行 Reindex；若要求可快速业务回切或需大规模架构改造，选择新建 3.7 域并迁移。
  • Amazon OpenSearch Service 不支持从 Elasticsearch 7.10 直接升级到 OpenSearch 3.7，必须经过 OpenSearch 1.x 和 2.19。
  • OpenSearch 3.x 不能读取由 Elasticsearch 7.10 或 OpenSearch 1.x 创建的索引。仅升级集群版本不会改变索引的创建版本。
  • OpenSearch 2.19 是关键中转站：它既能读取旧索引，也能创建可被 3.7 读取的新索引。
  • 原地版本升级为 AWS 托管的蓝绿部署。域通常保持服务，但会消耗额外资源，期间可能出现延迟和拒绝率上升，应安排变更窗口并设置停止条件。
  • 版本升级完成后不能原地降级；每一跳都必须完成测试、快照、升级预检查和业务准入。

2. 范围、假设与关键事实

2.1 适用范围

  • 源端为 Amazon OpenSearch Service 托管的 Elasticsearch 7.10 域。
  • 目标为同一个域原地升级到 Amazon OpenSearch Service 的 OpenSearch 3.7。
  • 覆盖热、UltraWarm、冷存储中的业务索引，以及普通、隐藏和关闭索引的盘点。
  • 不包含跨区域迁移、跨账号迁移、Serverless 迁移或自建 Elasticsearch 迁移。

2.2 三条必须接受的技术事实

事实对方案的影响
支持的原地升级链路有版本约束采用 ES 7.10 → OS 1.3 → OS 2.19 → OS 3.7，不跳级；每一跳单独发起并观察。
3.x 只兼容由 2.x 或 3.x 创建的索引进入 3.7 前，所有 7.10 / 1.x 创建的索引必须被删除或在 2.19 上重建。
升级成功后不能原地降级回退不是“点一下降级”，而是从兼容快照恢复到新建的旧版本域并切换流量。
边界说明：文档中的命令为模板。域名、索引名、请求速率、分片数、实例规格、维护窗口和报警阈值必须以客户压测结果为准。正式变更前，以 AWS 控制台或 API 返回的升级资格检查结果作为最终依据。

3. 路径选择与决策建议

方案 A：在 2.19 等待 ISM 淘汰

日志场景首选无需业务索引 Reindex

升级到 2.19 后持续写入新滚动索引，等待所有由 7.10 / 1.x 创建的历史索引按保留策略删除，再升级到 3.7。

适合：时间序列日志、固定保留期、允许在 2.19 停留一个完整保留周期、无必须长期保留的旧索引。

主要代价：项目周期至少增加“最长保留期 + 安全缓冲”；必须严密证明旧索引已清零。

方案 B：2.19 上选择性 Reindex

通用方案消耗 CPU / IO / 存储

短保留期日志自然淘汰；长期索引、持续读写索引和法规保留数据在 2.19 上逐个 Reindex。

适合：日志与业务索引混合、不能等待完整保留周期、存在长期历史数据。

主要代价：限流、数据一致性处理、容量扩容、别名切换和逐索引验收。

方案 C：新建 3.7 域并迁移

回切能力更强双域成本

创建独立 3.7 域，通过快照恢复、Migration Assistant、管道或双写搬迁可兼容数据，完成验证后切流。

适合：需要快速业务回切、同时改网络/加密/拓扑、容量重构、无法承受原地升级不确定性。

主要代价：双域费用、迁移链路、增量同步和流量切换设计。

5. 升级前评估与基线采集

5.1 资产清单

  • 域配置：区域、VPC、节点类型与数量、专用主节点、多可用区、EBS、UltraWarm、冷存储。
  • 安全：细粒度访问控制、IAM 资源策略、SAML/Cognito、TLS 策略、静态加密、KMS 密钥、审计日志。
  • 数据：索引创建版本、状态、存储层、大小、主分片/副本、保留期、写入速率、是否可删除。
  • 应用：读写客户端、SDK、Dashboards、Logstash、Beats、Fluent Bit、Firehose、CloudWatch Logs、Data Prepper 和自研采集器。
  • 功能：ISM、索引模板、组件模板、Ingest Pipeline、告警、异常检测、SQL/PPL、k-NN、跨集群搜索、快照仓库。
  • 运维：报警、值班人、变更窗口、业务冻结期、升级失败和升级成功后的回退流程。

6. 分阶段实施手册

6.1 通用变更前检查（每一跳重复）

  1. 确认集群为绿色，所有主分片和副本已分配，没有长时间 pending task。
  2. 确认 JVM 和磁盘满足 AWS 升级校验；同时预留蓝绿部署、分片搬迁和写入增长的额外空间。
  3. 暂停非必要批处理、批量删除、Force Merge、大规模 Reindex 和高负载查询。
  4. 完成手工快照并验证成功；记录域配置、模板、管道、策略、角色映射和关键 API 输出。
  5. 执行 AWS 的升级资格检查，清除全部阻断项。
  6. 确认客户端重试采用指数退避并设置合理超时，值班、监控和业务验证人员已到位。

6.2 第一跳：Elasticsearch 7.10 → OpenSearch 1.3

  1. 在非生产域完成同配置演练，验证 Elasticsearch 兼容模式下现有客户端行为。
  2. 在变更窗口发起版本升级，持续观察蓝绿部署状态、集群健康和业务指标。
  3. 升级完成后验证读、写、搜索、聚合、模板、告警、ISM、Dashboards 与安全认证。
  4. 至少完成一个高峰周期观察，再开始客户端改造和下一跳。
不要把兼容模式当成长期方案：OpenSearch 3.0 已移除主版本响应覆盖兼容设置。客户端必须在最终升级前完成 OpenSearch 化，并显式测试 3.7。

6.3 中间改造：去除 Elasticsearch 7.x 依赖

  • 迁移到与目标版本兼容的 OpenSearch 客户端，或经验证的标准 HTTP 调用。
  • 移除 mapping type、_type、include_type_name 和类型化 API。
  • 关闭节点嗅探，统一访问 Amazon OpenSearch Service 域端点；使用 IAM 时保留 SigV4 签名。
  • 通过逻辑别名或数据流访问滚动索引，避免应用绑定物理索引名。
  • 检查 3.x 的文档 ID、JSON、嵌套查询、系统索引访问、SQL/PPL、k-NN 和 Dashboards 变更。

6.4 第二跳：OpenSearch 1.3 → OpenSearch 2.19

  1. 确保客户端已通过 2.19 兼容测试，不再依赖 1.x 兼容行为。
  2. 重复通用变更前检查并执行升级。
  3. 升级完成后主动触发一次日志 rollover，确认新索引确实在 2.19 创建并正确挂载模板、别名和 ISM 策略。
  4. 冻结索引创建版本清单，分流进入方案 A（等待淘汰）或方案 B（选择性 Reindex）。

6.5 第三跳：OpenSearch 2.19 → OpenSearch 3.7

  1. 确认不存在任何由 Elasticsearch 7.10 或 OpenSearch 1.x 创建的索引；包括隐藏、关闭、UltraWarm 和冷存储索引。
  2. 处理 3.x 不兼容索引设置，例如已废弃的部分 k-NN 设置；以 AWS 升级预检查清单为准。
  3. 清理手工快照仓库中与 3.x 不兼容的旧版本快照；为最终升级保留经验证的 2.19 恢复点。
  4. 验证 Dashboards 对象和 3.x 行为变化，特别是旧可视化、Notebook、SQL 和系统索引访问。
  5. 发起升级并观察。完成后执行全套技术和业务验收，持续观察至少 72 小时。
最终准入门：AWS 升级资格检查通过 + 旧创建版本索引为零 + 2.19 快照验证成功 + 应用 3.7 回归通过 + 容量与监控就绪。

7. 日志场景：在 2.19 等待 ISM 淘汰旧索引

该方案用“时间”替代“重建计算”：让所有旧索引按业务既定保留期自然退出，确保进入 3.7 时只剩由 2.19 创建的索引。

7.1 适用条件

  • 所有待淘汰数据均为滚动日志或时间序列数据，删除后不再要求在线检索。
  • 每个索引模式都有明确、已生效且已验证的 ISM 删除策略。
  • 保留期和最长历史索引年龄可准确计算；没有被排除、解绑策略或人工保留的例外索引。
  • 允许域在 2.19 停留至少一个最长保留周期，并留出 ISM 作业调度和故障缓冲。
  • 不存在必须长期保留的 7.10 / 1.x 业务索引；否则该部分转入方案 B。

7.2 实施步骤

  1. 建立旧索引基线：在刚升级到 2.19 时导出全部索引创建版本，标记每个旧索引的预计删除日期、ISM 策略和责任人。
  2. 验证新索引链路：手工或按计划 rollover，确认模板、映射、别名、ISM policy、分片副本和存储层迁移均正确。
  3. 持续观察：每天统计旧创建版本索引数量与容量，监控 ISM 失败、集群红色、策略未附加和删除积压。
  4. 处理例外：对到期未删除的索引查明原因；业务批准后人工删除，或转为 Reindex，不得仅从统计表中忽略。
  5. 双重证明：旧索引清单为零后，再运行 AWS 3.7 升级预检查。只有两者同时通过才可进入最终升级。

7.3 等待时间计算

最早可升级日期 ≈ 2.19 首个合规新索引创建时间 + 最长在线保留期 + ISM 调度/故障缓冲。
例：日志最长保留 90 天，建议计划至少 90 天再加 7 至 14 天缓冲；实际以客户策略和升级预检查为准。

7.4 每日/每周检查模板

检查项通过标准异常动作
旧创建版本索引数量单调下降，最终为 0定位索引和策略；确认保留例外或 ISM 失败
新滚动索引创建版本全部由 2.19 创建检查写入别名、rollover、模板优先级和采集端索引名
ISM explain 状态无长期 failed / retrying修复权限、策略条件、集群健康或存储层问题

业务保留要求与实际删除一致需要保留则归档或转 Reindex 路径
 
# 示例：查看某个日志模式的 ISM 执行状态
GET _plugins/_ism/explain/logs-*?show_policy=true

# 示例：再次导出所有索引的创建版本

8. 需要保留数据时的 Reindex 方案

8.1 索引分类

类别特征处理方式
A：短保留日志按时间滚动、固定保留期在 2.19 自然淘汰，通常不 Reindex
B：只读历史索引长期保留、已停止写入低峰批量 Reindex，校验后切别名
C：持续写入业务索引存在新增、更新或删除双写/变更回放，或短暂停写后最终追平与切换
D：UltraWarm / 冷索引不在热存储按服务能力迁回可写层后重建，或归档/删除；先做成本评估

8.2 标准步骤

  1. 导出源索引 mapping、settings、别名和文档数；在 2.19 创建目标索引。
  2. 显式配置目标 mapping/settings。_reindex 只复制文档，不会自动复制完整配置。
  3. 用小索引压测安全吞吐，确定 requests_per_second 和并发任务数。
  4. 后台执行 Reindex，监控任务、集群资源、拒绝数和业务延迟。
  5. 对只追加数据执行增量追平；对更新/删除数据使用双写、变更回放或短暂停写完成最终一致性。
  6. 校验文档数、时间范围、抽样文档、核心聚合和业务查询。
  7. 原子切换别名或应用配置。保留旧索引到约定回退窗口结束，再删除释放空间。

8.3 容量与性能

  • 同域重建期间源、目标索引同时存在，必须预留目标数据、段合并、事务日志和蓝绿操作的容量。
  • 大型索引优先串行或小并发处理；根据 CPU、JVM、磁盘、拒绝数和 P99 延迟动态调速。
  • 不要在版本蓝绿部署、节点替换、大规模分片迁移或快照高峰时同时执行 Reindex。
  • 若容量无法支撑同域双份数据，应考虑临时扩容、分批删除旧索引，或采用方案 C。
物理索引名风险：若应用直接访问物理索引名而非 alias，无法无感原子切换。应先完成应用逻辑名改造，或为切换安排停写和配置发布窗口。

9. 应用、采集端和功能兼容性

检查域重点验证方法
SDK / RESTOpenSearch 客户端、SigV4、超时、重试、Bulk 响应解析、版本识别在 1.3、2.19、3.7 测试域逐级回归
索引 APImapping type、模板优先级、别名、rollover、数据流、动态 mapping创建测试索引并比对最终 settings/mappings
采集组件Logstash/Beats/Fluent Bit/Firehose/Data Prepper 插件与认证持续写入、故障重试、积压恢复、重复数据测试
查询DSL、SQL/PPL、脚本、聚合、Nested、Scroll/PIT黄金查询集比对结果与性能
DashboardsSaved Objects、旧可视化、Notebook、租户和角色映射导出备份后在 3.7 测试域导入并人工巡检
插件功能ISM、告警、异常检测、k-NN、跨集群能力执行端到端场景，不只验证页面能打开

9.1 OpenSearch 3.x 定向检查

  • 3.0 移除了版本响应兼容设置 compatibility.override_main_response_version。
  • Bulk API 对超长文档 ID 的限制更严格；扫描生成 ID 的所有写入方。
  • 系统索引访问控制发生变化；应用不应依赖直接读写系统索引。
  • 部分旧 k-NN 索引设置在 3.x 不再支持，需按升级预检查修复。
  • JSON 解析和嵌套查询的安全限制变化可能使边界请求失败，应加入负面测试。
  • 部分 Dashboards 旧组件和 API 已移除或迁移，必须验证保存对象而非只验证首页。

10. 监控、变更观察与停止条件

10.1 重点指标

集群层

  • ClusterStatus.red / yellow
  • CPUUtilization、JVMMemoryPressure
  • FreeStorageSpace、节点与分片分配
  • ThreadpoolSearchRejected、ThreadpoolWriteRejected
  • MasterCPUUtilization、MasterJVMMemoryPressure

业务层

  • HTTP 4xx/5xx、客户端超时和重试率
  • 读写吞吐、P95/P99 延迟
  • 采集积压、最新日志时间戳、丢失/重复
  • 核心查询正确率和 Dashboards 可用性
  • 业务 SLA/SLO 与错误预算

10.2 停止或降载条件

  • 集群进入红色、出现未分配主分片，或节点异常持续扩大。
  • 可用磁盘跌破客户预设安全水位，预计无法容纳分片搬迁或新写入。
  • 搜索/写入拒绝持续上升，P99 或业务错误率超过变更阈值。
  • Reindex 导致线上 SLA 受损：立即 rethrottle、暂停任务或取消任务，并保留现场指标。
  • 关键业务验证失败：停止后续跳转，保持当前已成功版本并执行问题修复。
说明：版本升级已进入 AWS 托管蓝绿阶段后，不应通过高风险人工操作干预。升级失败通常由服务自动回滚；如状态异常或长时间无进展，联系 AWS Support。

11. 回退、快照与容灾设计

场景回退策略
升级资格检查失败不发起升级；修复阻断项后重跑检查。
升级执行失败AWS 通常自动回滚到原版本；保持业务观察并联系 Support。
升级成功但应用不兼容优先回滚应用版本或关闭新功能；域不能原地降级。
必须回到旧引擎版本新建兼容旧版本域，从该版本可用快照恢复，验证后通过 DNS/应用配置切流。
Reindex 切换失败别名切回源索引；因此旧索引应保留到回退窗口结束。

11.1 快照原则

  • 每一跳前创建并验证手工快照，不只依赖自动快照。
  • 记录快照所需的目标引擎版本和恢复演练结果；快照兼容性受版本约束。
  • 最终升到 3.7 前，按 AWS 要求清理手工仓库中的 7.10 / 1.x 不兼容快照，并保留可用于 2.19 回退的新恢复点。
  • 域配置、IAM/角色映射、Dashboards 对象和应用配置应另行导出，因为数据快照不是完整环境备份。

12. 排期建议

以下为相对排期。实际时间由数据规模、测试覆盖、变更审批和方案 A 的最长保留期决定。

第 1–3 周
发现与方案设计：资产盘点、创建版本清单、应用扫描、容量评估、基线和回退设计。
第 2–5 周
非生产演练：三跳完整演练、客户端改造、3.7 回归、故障和恢复测试。
第 6 周
生产第一跳：7.10 → 1.3，业务验证和稳定观察。
第 6–9 周
客户端灰度：OpenSearch 客户端、采集端、查询与 Dashboards 改造上线。
第 10 周
生产第二跳：1.3 → 2.19，触发新 rollover 并确认创建版本。
保留期 + 缓冲
方案 A：等待 ISM 自然删除全部旧索引；或方案 B：分批 Reindex 长期索引。
最终窗口
生产第三跳：2.19 → 3.7，全量验收并观察至少 72 小时。
排期控制：不要把 OpenSearch 2.19 当作长期终态。AWS 在 2026 年 8 月公告中为 Elasticsearch 7.10、OpenSearch 1.3 和 2.19 等版本提供了额外升级缓冲，并说明相关安全与操作系统补丁覆盖延续至 2027-11-07、按更新后的支持费率计费。项目不应把该日期当作目标完成日，而应预留组织冻结期和至少一次延期缓冲。

13. 风险清单与缓解措施

风险影响缓解措施
遗漏旧隐藏/关闭索引3.7 预检查失败，计划延期使用 expand_wildcards=all 盘点；以 AWS 预检查做第二道门。
ISM 未实际删除方案 A 等待后仍无法升级逐索引记录 policy、状态和预计日期；报警 failed/retrying；保留方案 B 兜底。
客户端依赖兼容模式3.7 后写入或监控中断在 1.3/2.19 阶段完成 OpenSearch 化；3.7 测试域全链路压测。
Reindex 资源争用查询延迟和拒绝上升小流量标定、限速、低峰运行、串行大索引、必要时临时扩容。
持续写索引数据不一致丢更新、删除未同步双写/变更回放或短暂停写；只追加索引才使用时间戳追平。
蓝绿部署容量不足升级失败或耗时显著增加提前清理空间、降低分片压力、扩容并等待稳定后再升级。
版本成功后无法原地降级恢复时间较长完整演练、手工快照、新域恢复流程和 DNS/配置切流预案。
旧快照与 3.x 不兼容最终升级被阻断或恢复误判仓库分阶段治理；记录兼容矩阵；最终使用 2.19 恢复点。
Dashboards/插件对象不兼容运维能力或用户功能受损保存对象导出、测试域升级、逐看板和逐工作流验收。

14. 验收标准与交付物

14.1 最终验收标准

  • 域版本为 OpenSearch 3.7，配置变更状态正常，集群持续绿色。
  • 所有主分片与副本正常，节点、磁盘、JVM、拒绝数和业务延迟处于批准范围。
  • 核心读写、Bulk、查询、聚合、ISM、告警、Dashboards、认证授权和采集链路通过。
