01 · Why this design exists

为什么需要这个方案：HNSW 很快，但它用内存换速度

要理解 memory optimized，先要理解向量搜索为什么会贵。问题并不是向量文件本身特别大， 而是为了让查询足够快，HNSW 会额外构建一张需要频繁访问的“导航图”。

先从一次向量查询说起

文本、图片或视频经过 Embedding 模型后，会变成一串数字，也就是向量。 当用户提交一条查询时，系统需要从数十亿条向量中找出最相似的几条。 如果逐条比较，结果最准确，但数据量一大，查询时间和 CPU 消耗都无法接受。

第一步：把内容变成向量

Vector

可以把向量理解为内容在“语义地图”中的坐标。内容越相似，坐标通常越接近。

第二步：建立快速导航图

HNSW

HNSW 像城市道路网。查询不再挨家挨户搜索，而是沿着相似向量之间的连接快速接近目标。

第三步：把常走的路放进内存

低延迟

内存访问比磁盘快得多。图放在内存中，查询才能快速“跳转”，这就是 HNSW 高性能的来源。

通俗地说： 原始向量像城市中的所有房屋，HNSW 图像一张导航地图。 地图放在桌面上，找路很快；地图收进档案柜，每次查询再翻出来，成本更低，但速度会受影响。

为什么数据越多，内存会成为成本大头

HNSW 不只保存压缩后的向量，还要为每条向量保存与其他向量的连接关系。 这些连接会随着向量数量近似线性增长。到百亿级规模后，即使向量已经做了 16x 压缩， HNSW 图和量化码仍可能需要数 TiB 内存。 

本客户每条向量的常驻内存
= 1.1 ×（2-bit 量化码 + HNSW 图连接）
= 1.1 ×（0.25 × 1024 + 8 × 16）
= 422.4 bytes/vector

150 亿条向量需要的常驻内存
= 422.4 × 15,000,000,000
≈ 5.76 TiB

5.76 TiB 不是磁盘容量，而是向量检索所需的常驻内存量。 为了容纳这些内存，集群必须选择 r8g 这类内存优化实例，并部署足够多的数据节点。 因此，在百亿级向量场景中，购买计算节点的主要原因往往不是 CPU 不够，而是需要“买足内存”。

方案由此产生

真实业务中的数据通常并不是同样热门。新内容、近期内容或高价值内容被频繁搜索； 很久以前的历史内容可能一天只被查几次。如果仍然要求全部 150 亿向量的 HNSW 图一直常驻内存， 就相当于为低频数据长期保留昂贵的“前台座位”。

memory optimized 的出发点： 热数据继续把 HNSW 图放在内存中，保障查询速度； 温数据不再强制把完整图常驻内存，需要查询时再通过 mmap 和操作系统 page cache 读取。 用可接受的温层性能下降，换取更低的内存需求。
02 · Workload fit

什么场景才适合：先确认数据确实有“冷热差异”

这不是一个打开后就能普遍降本的开关。它要求业务能够识别哪些数据必须快、哪些数据可以慢一点， 并且查询可以尽量只访问需要的那一层。

一个适合的业务例子

以内容搜索为例，最近三个月的视频和热门内容贡献了大部分查询，这部分是热数据； 更早的历史内容仍然需要保留，也偶尔会被用户搜索，但访问频率明显更低，这部分是温数据。 两类数据都需要向量检索，但服务等级可以不同。

数据层业务特征技术策略通俗理解
热数据 查询频繁、P95/P99 要求严格、影响核心用户体验 memory_optimized_search=false，图常驻内存 把经常使用的资料放在手边，随时可以拿到。
温数据 低频访问、允许更高延迟、仍需保留近似最近邻（ANN）top-k 能力 memory_optimized_search=true，按需读取 把不常用资料放进档案柜，需要时再取。

满足这些条件，方案才值得评估

适合：可以明确区分冷热

  • 80/20 或 70/30 热度分布明显，大部分历史向量低频访问。
  • 索引能按时间、租户、内容类型或业务域拆分，热度边界比较稳定。
  • 应用知道应该查热索引、温索引，或者两者都查。
  • 温数据需要 top-k 相似搜索，但允许更高 P95/P99，也就是较慢的尾部请求，以及冷启动波动。
  • 写入以追加为主，历史索引封存后只读或低频更新。
  • 希望保持单个 OpenSearch domain 和较小的应用改造量。

不适合：所有数据都要求同样快

  • 每个请求都必须搜索全部 150 亿向量，无法按业务范围缩小搜索空间。
  • 温层也有持续高 QPS、严格尾延迟或秒级恢复要求。
  • 主要任务是窄半径去重、阈值判存或要求极高 top-1 命中率。
  • 数据冷热变化很快，需要频繁移动文档或重建 HNSW 图。
  • 无法用真实查询集验证召回率、冷启动和混合流量性能。
  • 目标是仅靠一个设置获得 50% 以上成本下降。

为什么“可以路由查询”特别重要

OpenSearch 会把大索引切成多个 shard，也就是分片。本客户按 50 GiB 分片估算约有 1,308 个分片。 如果一个查询同时访问全部分片， 每个分片都要执行一次局部搜索，再由协调节点汇总结果。这种模式称为 fan-out。分片越多，CPU、线程池排队和结果归并开销越大。

通俗地说： 查询 10 个分片像同时问 10 家门店有没有货；查询 1,308 个分片则像同时打电话给 1,308 家门店， 即使每家回答得很快，发起请求和汇总答案本身也会很慢。

用四个问题判断是否适合

判断问题理想答案如果答案是否定的
是否有至少 50% 至 70% 的低频历史数据？是可释放的常驻内存有限，收益可能不值得复杂度。
温数据是否允许更高延迟和更长冷启动？是应继续使用全热，或为温层保留更多节点和缓存。
查询是否能按时间、租户或内容类型路由？是全库 fan-out 可能成为比内存更严重的问题。
是否能执行真实数据 POC？是不能仅凭计算器结果直接上线。
本客户的初步匹配度： 假设 70% 历史向量确实低频，查询可以按业务范围路由，并接受温层降低 CPU 配比， 则该方案适合进入 POC。此时它是一种“热数据保体验、温数据换成本”的折中，而不是统一降低所有数据的服务等级。
03 · How it works

方案如何工作：数据还在，只改变“如何使用内存”

memory optimized 不会删除向量，也不会把温数据变成普通文本索引。 它保留 HNSW 向量索引和本地 EBS 数据，只是不再要求温层的完整图一直占用 native off-heap。 热层和温层可以部署在同一个 OpenSearch domain，也就是同一个托管集群和访问端点中。

技术表达

热索引走传统 Faiss HNSW 路径，图常驻 native off-heap； 温索引启用 memory_optimized_search，通过 mmap 按需访问索引文件， 由 OS page cache 缓存近期使用的数据页。

通俗表达

热数据的导航图一直摊在桌面上，查询最快； 温数据的导航图放在档案柜，需要时取出常用页面。最近查过的内容会暂时留在手边，所以越查越快。

这不等于完全不用内存： 温索引仍会使用操作系统内存作为 page cache。区别在于，内存从“必须长期完整占用” 变成“按实际访问热度动态缓存”。缓存未热时，需要更多磁盘读取，查询会变慢。

数据如何从热层进入温层

1

写入热索引

新数据进入按时间或业务边界创建的热索引，mos 关闭，保障新内容低延迟检索。

2

封存与稳定

达到大小或时间阈值后执行 rollover，也就是创建新索引继续写入，旧索引停止增长。随后完成 segment 合并、快照和质量校验。

3

切换为温索引

关闭索引，设置 index.knn.memory_optimized_search=true，再重新打开。该设置为静态索引设置。

4

分层查询与预热

默认请求只查热 alias；需要历史召回时再访问温 alias。节点替换后用真实代表性查询集分批预热。

04 · Technical implementation

技术实现：把几个容易混淆的概念说清楚

下面保留生产设计需要的技术术语，同时给出更直观的解释，便于非 OpenSearch 专家参与评审。

术语技术含义通俗理解
native off-heap JVM 堆外、由 Faiss 等 native library 使用的内存，传统 HNSW 图主要占用这里。 不是 Java 应用自己的工作区，而是一块专门给向量引擎使用的高速内存。
mmap 把磁盘文件映射到进程地址空间，查询时按需读取具体数据页。 像给大型档案建立页码，需要哪一页就取哪一页，不先把整柜文件搬到桌面。
OS page cache 操作系统自动使用空闲内存缓存最近读取的磁盘页。 刚取过的档案暂时留在桌面，下次再用就不用重新去柜子里找。
rescore 先用压缩向量找到候选，再读取更高精度向量重新打分。 先快速圈出候选，再对少量候选做精细复核，提高最终排序质量。
circuit breaker 限制 k-NN native memory 使用量的保护阈值，超限时可能触发索引驱逐。 内存的安全线，不是提前为某项工作锁定好的专属空间。

热层

性能优先

图常驻内存；on-disk rescore 仍可能读取全精度向量；CPU 预算按每个分片约 1 个 vCPU 起步。

温层

成本优先

图不进入传统 native cache；访问依赖 page cache 与 EBS；低频场景可从每个分片约 0.3 个 vCPU 起测。

共享资源

需要隔离策略

两层共享 CPU、page cache、磁盘 IOPS 与 search thread pool，必须限制 fan-out 和温层并发。

八个关键设计点

#设计点方案要求
1引擎与方法memory optimized 仅用于 Faiss HNSW 路径；当前方案不采用 IVF 或 PQ。
2静态设置切换需要 close / update setting / open，建议只对封存索引执行。
3Circuit breaker按热层常驻内存需求加 1.5 至 2 倍余量计算，不能把 CB 简单理解为 page cache 预留。
4page cache温层图访问与两层 rescore 都可能使用 page cache，热温混部需要测互相干扰。
5IOPS主要改善冷态恢复与半热态吞吐；完全热态通常由 CPU 决定。
6fan-out索引按可路由业务维度拆分，单请求应避免命中数百个 shard。
7召回标准 top-k 可作为主要目标；窄半径去重需单独验证，不沿用 top-k 的召回结论。
8高可用附件使用 0 replica 仅适合作为成本下限。生产配置必须按 SLA 重新评估副本。
05 · Sizing model

现在代入客户数据：15B 规模会得到什么结果

前面说明了为什么需要分层、什么场景适合以及方案如何工作。 这一节再代入附件中已经确认的客户参数，观察内存下降是否真的能转化为节点和成本下降。

每向量常驻内存
= 1.1 × (0.25 × dimension + 8 × m)
= 1.1 × (0.25 × 1024 + 8 × 16)
= 422.4 bytes/vector

全热常驻内存
= 422.4 × 15,000,000,000
≈ 5.76 TiB

2. 70% memory optimized 后的常驻内存

热向量数量
= 15B × 30%
= 4.5B

热层常驻内存
= 422.4 × 4.5B
≈ 1.73 TiB

释放的传统 HNSW 常驻内存
≈ 5.76 - 1.73
≈ 4.03 TiB

3. 混合 CPU 需求

热分片：约 392 × 1.0 vCPU/shard = 392 vCPU
温分片：约 916 × 0.3 vCPU/shard = 275 vCPU

混合 CPU 需求 ≈ 667 vCPU
等效 blended CPU:shard ≈ 0.51

4. 三约束装箱

约束需求对 24 × r8g.12xlarge 的判断结论
常驻向量内存约 1.73 TiB节点总向量内存能力明显充足非瓶颈
CPU约 667 vCPU总 1,152 vCPU，需给搜索和协调留余量部分约束

为什么省了 4.03 TiB 内存，账单只降 12.9%： 节点数是内存、CPU、存储三者约束的最大值。当前优化释放的是已经不再决定节点数的资源， 而全量 EBS 数据和混合查询 CPU 仍在同一批 r8g 节点上。

07 · Risks and controls

主要风险与控制措施

memory optimized 将显性内存成本转换为对缓存热度、磁盘随机读和调度隔离的要求。

风险客户影响控制措施优先级
冷启动与节点替换 同一索引冷热态吞吐可相差数量级，扩缩容后温层 P99 可能突增。 用真实查询预热；记录 kb/query；按 P99 制定变更窗口；提高 IOPS 只作为冷态恢复手段。 P0
热温 page cache 竞争 温层扫描可能挤压热层 rescore 所需缓存，导致热层延迟抖动。 限制温层并发；按 alias 分开查询；设置流量闸门；POC 必须混部测试。 P0
温层 CPU 0.3:1 未验证 成本模型成立，但实际 QPS 与 P95 可能不满足业务。 压测 0.3、0.5、1.0 三档，选择满足 SLA 的最低档位。 P0
分片 fan-out 协调节点归并、search queue 和尾延迟显著上升。 按租户、内容类型或时间桶拆索引；使用 routing；禁止默认全量 alias 查询。 P1
召回适用范围 标准 top-k 结果不能代表窄半径去重或 top-1 判存。 用客户 ground truth 分场景测 Recall@K、NDCG、top-1 和径向命中率。 P1
0 replica 任一主分片不可用时，相关数据在恢复前无法查询。 把当前配置视为成本下限；按 RTO/RPO 评估 1 或 2 replica，并重新运行计算器。 P0
单节点故障域 大规格节点故障影响分片多，恢复读取量大。 比较 24 × 12xl 与更多小节点；校验恢复时长、EBS 配额和 shard relocation。 P1

09 · Recommendation

推荐落地路径

建议采用“先同域验证，再按成本目标决定是否拆层”的两阶段路线。

A

第一阶段：同域 memory optimized

以 24 × r8g.12xlarge + 3 × m8g.xlarge master 作为 POC 起点； 热 30%、温 70%；热 1.0、温从 0.3 CPU:shard 起测。优点是端点和应用改造少，可快速验证真实收益。

B

第二阶段：按 KPI 分支

若同域方案满足 SLA 且约 13% 节省可接受，则保持单域；若要求 40% 以上节省，则评估双集群， 并接受查询路由、迁移和温层检索语义变化带来的额外代价。

C

生产化：补齐高可用

当前 0 replica 是成本下限，不是推荐生产配置。完成 POC 后按 SLA 加入副本， 重新评估数据节点数、EBS、IOPS、恢复时长和预留实例承诺。

不建议直接采购附件中的 0 副本配置。 该口径适合做方案间的相对成本比较。面向真实客户生产环境，最终 BOM 必须纳入副本、跨 AZ 故障、 快照恢复、峰值查询、扩缩容冷启动和实际部署区域价格。
