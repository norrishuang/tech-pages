九阶段部署流程

OpenSearch 的配置变更通过蓝绿部署完成，可用 DescribeDomainChangeProgress API 或控制台实时追踪。核心前提：整个过程在同一个 OpenSearch 集群内进行——绿节点加入现有集群，共享同一份 cluster state 与 routing table，集群规模临时翻倍。点击下方 播放 观看阶段推进与节点数变化。

2Creating a new environment创建绿环境的基础设施资源（如 Load Balancer）

端点切换与写入路由

端点切换发生在阶段 4。注意：域端点的 DNS 名称本身不变（形如 xxx.region.es.amazonaws.com），变化的是端点背后 Load Balancer 指向的后端节点。下图动画演示切换前后一条写请求的流向——切换后写入仍落在蓝节点的 primary shard 上。

绿节点作为协调节点，转发写请求至蓝节点 primary
切换后、Shard 迁移前：写入数据实际落在蓝节点的 primary shard 上，绿节点只是流量入口（协调节点）。无数据丢失，无写入歧义——去中心化架构下任意节点都能协调。

回滚行为：不会自动回滚

这是与 SageMaker、ECS 等其他蓝绿部署的关键区别。官方文档的表述 “maintains the original environment in the event that deployment is unsuccessful” 描述的是蓝环境在过程中被保留，而非“切换后异常会自动切回”。

阶段是否可回滚机制 / 影响
阶段 1–3（切换前失败）✅ 可回滚绿环境未接受流量，直接丢弃绿环境，蓝环境继续服务
阶段 4–6（切换后、迁移前）⚠️ 无自动回滚需人工干预；此时写入绿入口的数据若回滚有一致性风险
阶段 7–9（迁移中 / 后）❌ 无回滚路径蓝节点数据逐渐被清空后终止
ℹ️
版本升级的特殊保护：升级操作会在 pre-upgrade 检查后先做一次自动 Snapshot（托管 S3）。若升级在 pre-upgrade 阶段失败，服务从该 Snapshot 恢复。但这仅覆盖升级早期失败，不等于端点切换后的自动回滚。切换后写入绿集群的数据没有自动机制同步回蓝——零容忍场景应配合应用层双写或 Cross-Cluster Replication。

Shard 迁移期间的写入处理机制

Shard 从蓝节点迁移到绿节点使用 Peer Recovery 机制，分三个阶段。关键前提：整个迁移期间写入不被阻塞，shard 始终可写。点击标签逐阶段查看；动画演示数据流向。

PHASE 1
Segment 文件复制
大块数据传输，写入照常走蓝
PHASE 2
Translog 追赶 + 实时复制
双轨并行，写入不阻塞但延迟上升
PHASE 3
Primary Hand-off
cutover 瞬间，fencing 保证不丢写

Phase 1 — Lucene Segment 文件复制

  • 源 primary 记录当前 translog 位置 T0（checkpoint），执行 Lucene flush/sync，全量传输 segment 文件到目标绿节点。
  • 此阶段 所有写入照常走蓝节点的 primary shard，完全不受影响。
  • Phase 1 可能很耗时（大索引），期间新写入持续累积到 T0 之后的 translog。
  • 结束时：绿节点 shard engine 启动，目标 shard 加入 in-sync replication group，开始作为 replica 接收复制写。

Phase 2 — Translog 追赶 + 实时复制并行（双轨）

  • 源节点对 T0→T1 的 translog 取快照并批量发送给目标，目标 replay 追赶 Phase 1 期间的写入。
  • 同时，T1 之后的新写入通过正常 replica 复制实时到达目标节点。
  • 目标绿节点此刻 同时接收两路写入（批量 replay + 实时复制），都要同步写目标 translog。
⚠️
迁移期间唯一的性能影响：双轨写入竞争 translog 锁，导致 Phase 2 期间 写入延迟上升（OpenSearch issue #2729 记录的已知现象）。但写入 不会被阻塞或中断。

Phase 3 — Primary Hand-off（迁移 primary 时）

若迁移的是 replica：primary 留在蓝节点不变，旧 replica 移除、绿节点作为新 replica 加入——无 hand-off、无中断。若迁移的是 primary，则触发 hand-off，由三重 fencing 机制保证安全：

机制作用
Primary Term（主任期）单调递增整数，primary 每次变更 +1。replica 拒绝 term 低于当前的写——防止旧 primary 切换后继续写（防脑裂）
Sequence Number _seq_no每个写操作的全局唯一序号，追踪复制组中各 shard 进度
Global Checkpoint所有 in-sync replica 都已确认的最大 seq_no。≤ 该值的操作保证不丢、不需重放
✅
hand-off 瞬间不会丢写。 已 ACK 写入由 global checkpoint 保证安全；primary term fencing 防止旧 primary 继续写。极小概率的 in-flight 写入会收到可重试错误（如 503），客户端重试即可（幂等失败，非数据丢失）。

一句话总结

🧭
同一集群翻倍 → LB 切端点到绿节点（绿节点兼任 Data + Coordinator）→ 切换后写入经绿节点协调转发到仍在蓝节点的 primary → Shard 迁移走 Peer Recovery 三阶段：Phase 1 全量 segment 复制（写入照常走蓝）、Phase 2 translog 追赶 + 实时复制双轨（写入不阻塞但延迟上升）、Phase 3 primary hand-off（靠 primary term + global checkpoint 保证不丢写，极小窗口可能触发客户端重试）。全程写入不中断、已确认数据不丢失。
